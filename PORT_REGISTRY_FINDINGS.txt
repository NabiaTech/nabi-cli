2. ARCHITECTURE INSIGHTS
================================================================================

SCHEMA-DRIVEN PATTERN (Aura)
  Config Layer (TOML) → Transform → Derived State (JSON) → Runtime (Rust)
  
  ✅ Source of truth: TOML files (human-editable, version-controlled)
  ✅ Derived state: JSON registry (fast, validated, machine-readable)
  ✅ Audit trail: manifest.json (tracks which TOML files created registry)
  ✅ Separation of concerns: Python (transform/validate) + Rust (commands)

PLATFORM-AWARE DESIGN
  • Supports 4 platforms: macos, wsl, rpi, linux
  • Per-platform port overrides (e.g., loki: 3100 vs 3101 on WSL)
  • Per-platform endpoints (tailscale vs localhost)
  • Per-platform enabled/disabled flags
  • Cross-platform service detection

DATA FLOW
  1. User edits ~/.config/nabi/ports/*.toml
  2. Run transform_ports.py → validates TOML, generates JSON
  3. Commands read JSON from ~/.local/state/nabi/ports/registry.json
  4. Rust performs health checks, conflict detection, drift analysis
  5. Python validator cross-checks registry against running processes

5. RACE CONDITIONS & CONCURRENCY
================================================================================

IDENTIFIED RISKS:

  1. Registry Load Race (low risk)
     - No file locking on registry.json reads
     - Multiple concurrent `nabi port` commands could race
     - Mitigation: Python transformer is single-threaded, rarely called
     - Rust commands are read-only, safe to run in parallel

  2. Conflict Detection Gaps (medium risk)
     - Doesn't check ports HashMap field
     - Could miss conflicts if multi-port becomes standard
     - Mitigation: Multi-port not used yet, time to fix before adoption

  3. Drift Detection Window (low risk)
     - Snapshot-based, no historical tracking
     - --since flag exists but not implemented
     - No persistent state between runs
     - Not a safety issue, just limits forensic capability

SAFE OPERATIONS:
  ✅ Multiple concurrent `nabi port list/check/cross-platform` - Safe
  ✅ Multiple concurrent Python transforms - Unsafe (race to write JSON)
  ⚠️  Concurrent transforms + reads - Potential stale state
  ✅ Port shifts/migrations - Blocked by unimplemented execution

6. VALIDATION STRENGTHS
================================================================================

THREE-LAYER VALIDATION:

  Layer 1: Port Range Validation
  ├─ Checks port ∈ [3000, 8499]
  ├─ Validates integer type
  └─ Rejects out-of-range allocations

  Layer 2: Service Config Validation
  ├─ Required: port, purpose
  ├─ Optional: container_port, protocols, platforms
  ├─ Protocol validation: tcp, udp, http, https, websocket, sse
  ├─ Supports combined protocols: "http+sse", "ws+http+sse"
  └─ Platform override syntax checking

  Layer 3: Port Conflict Detection
  ├─ Detects duplicate port allocations
  ├─ Resolves platform-specific overrides
  ├─ Reports per-platform conflicts
  └─ Shows which services collide

HEALTH CHECKING:

  ✅ Listening Port Detection
  ├─ TCP connect test (is_port_listening)
  ├─ Timeout: 1 second per port
  └─ Works for both system processes and containers

  ❌ HTTP Health Endpoints
  ├─ Current: Only TCP connectivity check
  ├─ Missing: Health endpoint verification
  ├─ Would require: reqwest dependency
  ├─ Example: GET /ready for Loki, /api/health for Grafana

RUNTIME DETECTION:

  ✅ System Processes
  ├─ Uses lsof -i -P -n
  ├─ Parses process name, port, state
  ├─ Works on macOS and Linux

  ✅ Container Services
  ├─ Uses docker ps --format
  ├─ Extracts port mappings
  ├─ Maps external:internal ports
